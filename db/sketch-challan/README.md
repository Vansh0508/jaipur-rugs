# Sketch Challan module design

**Status (revised September 28, 2026):** migrations `001`–`004`, the Edge Functions and the typed client in `packages/db-management-client/src/sketch-challan.ts` were rewritten to match the running app. They are still **not applied or deployed**, and nothing here has run against a real database yet (no local Postgres was available). Apply them to a scratch project first, then follow the go-live plan in section 21.

**What the revision changed (supersedes the PDF-era text in sections 1, 2, 5, 13, 15 and 16 below):**

- **Intake:** the live NAV Excel refresh (`excel_upsert`) replaces the PDF upload. There is no Upper Manager, no PDF parser, no documents table and no 10-day retention. NAV leaves many fields blank, so blank is allowed. Only cells that have a value overwrite a challan, and fields the manager owns stay once set; that merge runs in the app (`lib/importExcel.ts`).
- **Roles:** Sketching Manager, Sketcher and Admin. Admin is the Hub's existing `Admin` role, bound as an app role. A role counts whether it comes from `employees.primary_role_id`, which is how the Hub assigns roles, or from a current `employee_roles` row. Exactly one Sketching Manager is allowed, counting both.
- **Tasks:** Done is a new `submitted` status; the Sketching Manager approves it (`completed`) or sends it back with a note (`assigned`, credit resumes). Only the current holder starts or submits. The manager is also on the sketcher roster, so the Sketching Manager may hold parts. Parts go only to active employees with the Sketcher or Sketching Manager role. Nothing happens to tasks while a challan is not active.
- **Changes after allotment:** the manager's request may be reason-only or carry a handover. Admin approves it, never their own. Admin adds extra parts and hands tasks over.
- **Columns added** so every form field is saved: `map_no`, `substitute_design`, `sketcher_remark`, `order_size`, `map_size_note`, `excel_fields`. Change requests gain `handover`.
- **Fixes:** `002` no longer fails on the ambiguous `description` column. RLS is enabled in `001`, so the tables are never left open. The task policy's `a.task_id = id` typo is fixed. Direct inserts into the append-only tables are revoked. A challan can't be completed until every part is approved. The due reminders are a pg_cron job (`004`) instead of a script holding the service-role key.

**Frontend target:** `apps/sketch-challan`  
**Database module:** `db/sketch-challan/`  
**Deployment:** Internal office server  
**Storage:** Internal self-hosted S3-compatible storage

## 1. Confirmed operating model

- There is one Upper Manager and one Sketching Manager.
- The Upper Manager is the only PDF uploader.
- One project/Production Order has one challan.
- A challan may contain multiple tasks assigned to multiple Sketchers.
- Complex designs can be divided into separately named parts for different Sketchers.
- A task has one active Sketcher at a time and can be transferred in emergencies.
- Sketchers cannot edit challan details or upload PDFs.
- Sketchers can start/complete tasks, comment, report a block and request clarification.
- Only the Upper Manager and Sketching Manager edit challan details.
- There is no Color Copy → Master Creation → Master Checking workflow. Those printed labels are retained only when reproducing the paper layout.
- Challans use simple states: Active, On Hold, Completed and Cancelled/Discarded.
- All data changes, transfers, comments, restores and status actions remain in permanent history.
- Source and attachment PDFs are physically deleted after 10 days; extracted data and file metadata remain permanently.
- Intake will later support a NAV/API source without changing the challan/task model.

## 5. Roles and delegated rights

Use the monorepo's existing `roles`, `employee_roles`, `permissions` and `role_permissions` tables. Do not create a parallel Sketch Challan role-assignment system. These roles are independent of `employees.manager_id` but remain part of the shared Hub authorization vocabulary.

Roles:

- `upper_manager`: exactly one active assignment globally; upload and full management rights.
- `sketching_manager`: exactly one active assignment globally; challan editing and task management rights.
- `sketcher`: multiple employees; task-only access.
- Existing Hub administrator: manages role assignments and permission bindings.

An employee may hold multiple app roles. Active uniqueness is per employee and role, not per employee.

Register these permission keys in the shared permissions catalog:

- `sketch_challan.upload`
- `sketch_challan.edit`
- `sketch_challan.tasks.manage`
- `sketch_challan.due_date.manage`
- `sketch_challan.hold.manage`
- `sketch_challan.complete`
- `sketch_challan.restore`
- `sketch_challan.export`
- `sketch_challan.read.all`
- `sketch_challan.roles.manage`

The administrator delegates rights by assigning one of the approved roles or changing that role's permission binding. A permission-matrix constraint prevents the Sketcher role from receiving upload, challan-edit, task-management, due-date, hold, completion, restore, read-all or role-management permissions. Sketchers receive only assigned-task read/action/comment permissions. Granting broader authority requires assigning an approved manager/admin role; the one-Upper-Manager and one-Sketching-Manager constraints still apply. Replacing either sole manager atomically expires the former shared `employee_roles` row and creates the new one.

## 6. Challan and task status

`sketch_challan_status`:

- `active`
- `on_hold`
- `completed`
- `cancelled`

`sketch_challan_task_status`:

- `assigned`
- `in_progress`
- `blocked`
- `clarification_requested`
- `completed`

There are no production stages beyond these statuses.

A completed challan can be reopened only by the Upper Manager or Sketching Manager, with a mandatory reason. Reopening creates a new version and returns the challan to `active`.

Discarding a challan changes it to `cancelled`; it does not delete extracted data, tasks, history or file metadata.

## 7. Multiple-Sketcher task delegation

The Sketching Manager creates one or more tasks inside a challan. Every task requires an `assigned_part`, for example Border, Center/Bicha or Color Adjustment.

- One challan can have many tasks.
- Each task has one active Sketcher assignment.
- Different tasks can be worked simultaneously by different Sketchers.
- The Upper Manager may also assign or transfer a Sketcher.
- A transfer closes the active assignment and creates a new assignment row.
- Previous Sketcher, part, timestamps, progress and reason remain visible in history.
- The new Sketcher receives an in-app notification.
- Existing comments and task updates remain attached to the task.
- Each assignment retains its assignee, start, handover/end date, reason and excluded leave/non-work dates. Workday credit is calculated from task Start to handover/completion, counting Monday–Saturday and excluding Sundays and recorded leave/non-work dates. A replacement receives no credit until starting the task.

Emergency delegation has no fixed expiry. It ends when the task is completed or when an authorized manager approves an early transfer/end.

## 8. Sketcher actions

Sketchers can only act on tasks currently assigned to them:

- View the challan and their assigned part.
- Mark a task In Progress.
- Mark a task Completed.
- Add a comment.
- Report Blocked with a reason.
- Request Clarification with a message.

Sketchers cannot:

- Edit extracted challan fields.
- Change due date, priority, hold state or challan status.
- Assign or transfer tasks.
- Upload or delete PDFs.
- Restore historical values.

Every Sketcher action creates an append-only activity event. Blocked, clarification and completion events notify the Sketching Manager.

## 9. Priority and dashboard ordering

`sketch_challan_priority`:

- `urgent`
- `high`
- `normal`
- `low`

Dashboard ordering:

1. Manual priority: Urgent → High → Normal → Low.
2. Within the same priority, earliest due date first.
3. Overdue challans are visually highlighted.

This puts urgent requests at the top while still respecting due dates.

## 10. Hold behavior

Upper Manager and Sketching Manager can place a challan on hold with a mandatory reason.

- Starting hold creates a hold-period row and changes status to `on_hold`.
- Resuming records the hold end time.
- Due date automatically extends by the elapsed hold duration, rounded according to the implementation's date policy.
- A manager may override the calculated due date; the override and reason are versioned.
- Multiple hold periods are retained and their durations are not lost.

## 11. Remarks and activity tab

The challan has one editable General Remark field plus an append-only activity tab.

The activity tab shows:

- Upload and extraction
- Detail changes
- General remarks and comments
- Task creation, assignment and transfer
- Task start/completion/block/clarification
- Due-date and priority changes
- Hold/resume
- Completion, reopening and cancellation
- Field-level or full-version restoration
- PDF retention deletion

Changes limited to Design Remarks, Substitute Remarks, Review Notes or General Remark do not notify the Upper Manager. They still appear in history.

## 12. Version history and restoration

Every manager edit creates an immutable challan version containing:

- Complete post-change challan snapshot
- Field-level old/new values
- Actor and frozen role/name
- Reason when required
- Timestamp

Upper Manager and Sketching Manager can restore:

- Individual fields, or
- An entire previous challan snapshot

A restore never deletes or rewrites history. It creates a new current version linked to the restored version. A reason is mandatory for full restoration and for restoring a completed/cancelled challan.

Version rows are append-only. Revoke UPDATE/DELETE from all database roles, including `service_role`, and add an immutability trigger.

## 13. Duplicate upload handling

Production Order No. is unique in Phase 1: one project, one challan.

When the PDF hash or Production Order No. already exists, show the Upper Manager a popup with:

- Cancel
- Open existing challan
- Create another challan from this PDF

Production Order No. remains strictly unique. “Create another” is allowed only after the uploader supplies or corrects the new challan to a different, unique Production Order No.; it acknowledges duplicate file content, not a second challan for the same project. The confirmation actor and timestamp are stored. The database uses an advisory lock during duplicate checking so concurrent uploads cannot bypass the prompt.

## 14. Notifications

Initial delivery is in-app only:

- Immediate popup
- Unread badge
- Notification/update tab
- Mark one as read
- Mark all as read

Notify for:

- Task assignment or transfer
- Task blocked, clarification requested or completed
- Due-date change
- Priority change
- Hold or resume
- Challan detail change by Sketching Manager, except changes limited to Design Remarks, Substitute Remarks, Review Notes or General Remark
- Challan completion, reopening or cancellation
- Upcoming due date at 3 days, 1 day and 0 days

Notification rows use a unique `dedupe_key` so retries cannot create duplicate popups.

An internal-server reminder worker runs daily and creates the 3/1/0-day notifications. Due-date edits, hold/resume, completion and cancellation invalidate future reminder keys and cause the worker to schedule only the currently applicable reminders.

## 15. PDF storage and retention

Only PDF files are accepted, maximum 10 MB each.

Document types:

- Original NAV challan
- Manager-added PDF attachment
- Generated printable challan

Rules:

- Only the Upper Manager uploads the original NAV PDF.
- Upper Manager and Sketching Manager may upload manager-added PDF attachments.
- Sketchers cannot upload any PDF.
- Files are stored on the internal self-hosted S3-compatible server.
- Unfinished work has no automatic PDF expiry. Completion or an explicit manager approval sets `retention_eligible_at` to ten days in the future.
- A retention worker permanently deletes only eligible physical objects when `retention_eligible_at` is reached and records `deleted_at` and deletion result.
- Extracted challan data, document metadata, checksum and activity history remain permanently.
- Cancelling/discarding a challan does not erase its data; PDFs still follow the 10-day retention rule.
- The application can regenerate a printable challan from stored digital data after the source PDF is gone.

Validate PDF magic bytes, MIME, size, encryption, JavaScript/embedded files and parser resource limits at upload. Use content-addressed, no-overwrite object keys. If database creation fails after upload, remove the unreferenced object best-effort and clean abandoned objects through a scheduled job.

## 16. Future API intake

`source_type` supports:

- `pdf`
- `api`

The task, history, notification, reporting and printable-output model is independent of source. When the NAV API is available, it populates the same typed challan fields and stores the external source ID and raw payload instead of requiring a retained PDF.

PDF intake records the authenticated Upper Manager as `created_by_employee_id`. API intake leaves that employee field null and records a frozen integration identity such as `NAV API` in `source_actor_label`; it must never falsely attribute an automated record to an employee.

## 19. RLS and write boundary

Frontend Supabase access is SELECT-only. Writes go through one Edge Function per capability, following the repository contract.

Visibility:

- **Sketching Manager and Admin (read-all permission):** all challans.
- **Sketcher:** challans with a current or former task of theirs, including the tasks they held before a handover. Each sketcher can read their own assignment history and credit.
- **Notification:** the recipient only.

Each Edge Function authenticates the Hub/Supabase session, resolves `employees.id`, checks the permission the action needs, and calls the service-role-only transactional RPC `sketch_challan_apply_action`. The RPC re-checks the role, the holder and the challan state. Internal helpers live in `private` with a pinned `search_path`. `sketch_challan_versions` and `sketch_challan_activity` are append-only: nobody can update or delete them, direct inserts are revoked, and immutability triggers catch anything else.

## 20. Write capabilities

These all go through `sketch_challan_apply_action` (003):

| Edge Function | Action | Who |
|---|---|---|
| `sketch-challan-create` | `excel_upsert`: live NAV Excel refresh | Sketching Manager (`refresh`) |
| `sketch-challan-update` | `update`: edit before allotment | Sketching Manager (`edit`) |
| | `request_update`: change or handover after allotment | Sketching Manager |
| | `review_update`: approve or reject | Admin (`change.approve`), never on their own request |
| | `remark`: sketcher remark | current part holder (`task.act`) |
| `sketch-challan-task` | `task_create`: allot parts | Sketching Manager before allotment, Admin after |
| | `task_status`: start or submit | current part holder |
| | `task_review`: approve or send back | Sketching Manager |
| | `task_transfer`: hand over | Admin |
| `sketch-challan-set-status` | hold, resume, complete, cancel, reopen | `hold.manage` / `complete.manage` |

Due reminders run inside the database (`004`, pg_cron, 09:00 IST). Export and print are client-side and need no write.
