## 1. Executive Summary & Strategic Vision

### 1.1 The "Why" & Organizational Alignment
DnD currently rebuilds the same fixed-format PowerPoint layout by hand for every rug design option, copying colour codes and spec values off a Tikni BMP file into a template one field at a time. This is repetitive clerical work that does not require design judgement — it is exactly the kind of operational friction the monorepo program exists to remove, freeing designers to spend time on the actual design intent and merchandising decisions instead of manual data entry.

> **Vision Statement:**
> A designer uploads the Tikni BMP and fills one short form; the tool reads the colour palette automatically, and downloads a ready-to-send PPTX + PDF layout in the correct B2C / JLI / B2B format — with the raw BMP never leaving the system.

### 1.2 Core Project Thesis
By solving **manual, repetitive PPT layout assembly from BMP design files**, we will enable **DnD designers** to **generate a finished, on-brand CAD layout in minutes instead of manually re-typing/re-colouring a deck per design option**, resulting in **reclaimed designer hours and fewer copy-paste/colour-mismatch errors** without changing DnD's approved layout formats.

### 1.3 Key Business Objectives (OKRs)
| Objective | Key Result / Target Metric | Measurement Baseline | Target Date |
|:---|:---|:---|:---|
| **O1:** Eliminate manual PPT assembly for CAD layouts | 100% of new B2C/JLI/B2B CAD layouts produced through the tool | Current: 0% (all manual) | `TBD` |
| **O2:** Reduce layout turnaround time per design option | `[DnD to confirm current avg. minutes/layout]` → target ≤ 5 min/layout including upload+review | Current: `[DnD to confirm]` | `TBD` |
| **O3:** Remove BMP leakage risk from customer-facing output | 0 raw BMP files present in any PPTX/PDF ever generated by the tool | Current: N/A (manual process, risk exists informally) | `TBD` |

## 2. Problem Statement & Root Cause Analysis

### 2.1 Current State ("As-Is")
- **Current Workflow:** Designer receives/creates a Tikni BMP → manually opens the fixed PPT template for the target format (B2C / JLI / B2B) → manually reads colours off the BMP in visual order (largest area first, by eye) → types GRC/ARS colour codes into numbered slots → manually retypes spec fields (size, shape, quality, fibre, dyeing, finish edge/pile/backing/wash, width, length, PD/PID/Project#, design code, date) → manually pastes in the reference/design-intent image(s) → exports PPT and PDF → shares with production/sales.
- **Friction Points:** Every field is retyped by hand per design option; colour-sequence-by-eye is error-prone; multi-file/multi-option decks multiply the manual work per slide; there is no enforced separation between the confidential BMP and the shared output (relies entirely on the designer remembering not to attach it).
- **Data Blindspots:** No system of record for which BMP/colours/spec values produced which layout — if a layout is questioned later, there is no audit trail back to the source file.
- **Tools in use today:** PowerPoint (manual), Tikni-generated BMP files, ad hoc project folders for reference images ("jaise abhi Bangalore ka project hai" — one folder per project, called out in the meeting as already messy).

### 2.2 Impacted Stakeholders
| Stakeholder Group | Role in Jaipur Rugs Ecosystem | How Current Problem Affects Them |
|:---|:---|:---|
| **DnD Designers** | Produce CAD layouts from Tikni files | Spend time on repetitive retyping instead of design work; risk of colour-sequence or spec-field mistakes |
| **R&D** | Possibly consumes the same layout format (unconfirmed, Section 2.5) | May inherit the same manual burden if they follow the same format |
| **Sales / Merchant-facing teams (B2C, JLI, B2B)** | Send the finished layout onward for approval/order | Depend on layout accuracy; currently have no guarantee the raw BMP wasn't accidentally included |
| **Corporate / Leadership** | Oversight of DnD throughput | No current visibility into how much designer time this consumes |
| **IT / Platform** | Monorepo, Hub, shared DB | New module + first-of-its-kind PPTX-editing/PDF-export server-side workload (see Section 4.4/8) |

### 2.3 Root Cause Analysis (5 Whys)
1. **Symptom:** Designers spend significant manual time per design option producing an identical-format PPT layout.
2. **Why?** Every colour code and spec value must be hand-typed into the template for each new BMP/design.
3. **Why?** There is no tool that reads the BMP palette and holds the fixed template's variable fields as structured form inputs.
4. **Why?** The layout has always been produced directly in PowerPoint by the designer, because that was the only tool available.
5. **Root Cause:** The variable data (colours, spec fields, reference images) and the fixed presentation (the PPT template) have never been separated into "data" vs "template" — so every new design forces a full manual re-entry into the presentation layer itself.

## 4. Solution Architecture & Scope Boundaries

### 4.1 In-Scope vs Out-of-Scope
| In-Scope (this project) | Explicitly Out-of-Scope |
|:---|:---|
| ✅ Upload one Tikni BMP per design; automatic palette extraction ordered by area (pending Section 2.5 item 4) | ❌ Editing/creating the Tikni BMP itself — that stays in whatever tool generates it today |
| ✅ Single-page form for variable spec fields, with dropdowns for standard-value fields | ❌ Free-form layout design / new template formats beyond the confirmed B2C, JLI, (assumed) B2B formats |
| ✅ Layout-variant picker: B2C / JLI / B2B | ❌ R&D-specific format, unless/until Section 2.5 item 3 confirms it's identical |
| ✅ Attach one or more reference/design-intent images per record | ❌ A shared network folder for reference images (explicitly rejected in the meeting — "isse messy ho jayega") |
| ✅ Multi-file / multi-design-option decks (one slide per option, same rug spec) | ❌ Bulk/batch conversion of historical PPT decks already produced manually |
| ✅ Download finished layout as PPTX and PDF | ❌ Emailing/distributing the finished layout automatically — download only, for now |
| ✅ Guarantee: raw BMP never appears in generated output | ❌ Building the self-hosted S3 object storage layer from scratch if it doesn't already exist for other modules (Section 8.3 flags this as an org-level gap, not something to solve inside this one PRD) |

### 4.2 Core Deliverables & Key Capabilities
1. **BMP palette extraction service:** reads an uploaded Tikni BMP's indexed colour palette and computes each colour's covered pixel area, producing an ordered colour list (ordering rule pending Section 2.5 item 4 confirmation).
2. **Colour code capture — target: auto-read; fallback: manual entry.** Target state (per the meeting, item 5 in Section 2.5): once DnD's team adopts writing the GRC/ARS code onto the Tikni file itself (as a legend), the tool reads it automatically alongside the palette extraction — no format/position for that legend has been shared yet, so the actual read mechanism (likely OCR against a fixed legend layout, TBD) is not designed in this PRD. **Until that's confirmed and DnD's team has actually adopted the practice, the form must support the designer typing the code against each detected colour manually** — this is the only path implemented in Phase 1 (Section 11), with auto-read added once Section 2.5 item 5 is resolved.
3. **Layout form:** one page, fields scoped to the chosen variant (B2C / JLI / B2B), dropdowns for standard-value fields (shape, pile type, backing, edge, wash — exact allowed-value sets pending the reference folder in Section 2.5 item 1), free text for the rest, multi-file attachment for reference images.
4. **Template-fill engine:** fills the existing DnD-approved PPTX templates (shape text runs + colour-slot solid fills) rather than generating a deck from scratch, preserving all fixed template content exactly as-is.
5. **PDF export:** server-side conversion of the filled PPTX to PDF.
6. **Storage:** uploaded BMP, reference images, and generated PPTX/PDF stored per-record, with the BMP itself never exposed through any download/share path.
7. **Admin surface:** any authorized admin can see every designer's records (not just their own) and a usage view — who has used the tool and how much (record count per employee) — see Section 4.3/8.5 for the visibility model.

### 4.3 End-to-End User / Operational Journey
1. **Trigger / Entry:** Designer opens the CAD Layout tile from the Hub launcher.
2. **AuthZ check:** Authenticated employee (`packages/auth`). Two visibility tiers, confirmed: a regular **creator** sees only the records they made; an **admin** sees every record across all designers, plus a usage view (record count per employee — who is using the tool and how much). See Section 8.5 for the RLS shape and Section 8.2 for how the admin flag is modeled.
3. **Processing:** Designer picks a variant (B2C/JLI/B2B), uploads the Tikni BMP, reviews the auto-extracted colour list and enters the GRC/ARS code against each (manually for now — see Section 4.2 item 2 for the auto-read target), fills the spec form, attaches reference image(s), optionally adds more design options (multi-file). All writes go through Edge Functions per AGENTS.md Section 4.
4. **Execution:** Template-fill engine produces the PPTX; PDF export runs server-side; both become downloadable.
5. **Resolution & Feedback:** Designer downloads PPTX + PDF; the record (form values, colour codes, attachments, generated files) persists for audit/reference — closing the "no audit trail" gap named in Section 2.1.

## 8. Data Model Plan (Track A) — AGENTS.md Section 3.1

Everything below is a **proposal for review**, not an applied schema — no migration has been written or run.

### 8.1 Technical design: how the templates get filled

**Findings from directly inspecting the two sample PPTX files (via `python-pptx`), which is the load-bearing evidence for this whole section:**

- Both templates hold their fixed labels and variable values as ordinary PowerPoint **text-box shapes** with plain text runs (no PowerPoint "content controls" / merge fields). E.g. JLI slide 1 has a `TextBox 19` shape whose paragraphs are literally `'14 ft X 19 ft'`, `'RCT'`, `'Hand Tufted HD'`, etc. — one paragraph per spec field, in a fixed order, sitting next to a sibling shape (`TextBox 18`) holding the matching labels (`'SIZE : '`, `'SHAPE : '`, …).
- **Colour slots are two things layered on one shape, not just text:** each numbered colour box (`#1:`, `#2:`, …) is a text box whose **solid fill colour is set to the actual swatch RGB** (confirmed via `shape.fill.fore_color.rgb` — e.g. JLI's `#4:` box has fill `#BDBDAE`), with the visible text being only the slot number (JLI: `"#4:"`) or slot number + yarn type (Disney/B2C: `"#4. Silk Wool Mix Ply"`). The GRC/ARS code the designer types must be appended into that same text run — the colour itself is represented by the shape's fill, not by text.
- **Conclusion for the fill engine:** this must be a template-fill approach that opens the existing `.pptx`, locates shapes by name/id/position, and (a) rewrites specific text runs with form values, and (b) sets specific shapes' `<a:solidFill><a:srgbClr val="RRGGBB"/></a:solidFill>` to the extracted palette colours — never regenerating slides from scratch, which would lose the fixed template content (labels, disclaimers, address block, approval/signature lines, policy text on the second B2C slide) that must stay byte-for-byte as-is per the meeting's explicit requirement.
- **Node implementation options (no code written yet, for review):**
  1. A library built for editing existing PPTX templates by shape name and swapping text/images (e.g. `pptx-automizer`) — preferred if it can also set a shape's solid fill colour; needs a spike to confirm.
  2. Fallback: treat the `.pptx` as a zip of OOXML, parse/edit the relevant `slideN.xml` (and `slideN.xml.rels` for images) directly with a fast XML library, then re-zip. More control, more code to maintain — use only if (1) can't set fill colours cleanly.
- **PDF export:** LibreOffice headless (`soffice --headless --convert-to pdf`) invoked server-side against the filled `.pptx`. This is why Section 4.4 requests a hosting exception — this does not run inside Vercel's serverless function model.
- **Same spike must also explain the unmatched colour-slot fills found in Section 8.4** (a handful of colour-slot shapes whose fill doesn't correspond to any colour in the sample BMP's palette) before the shape-mapping logic is finalized — see Section 8.4 for the two theories and why they need confirming, not assuming.

### 8.2 Entities & relationships (plain language, pending ERD review)
- A **cad_layout_record** belongs to one `employees.id` (creator), has one `variant` (b2c/jli/b2b), one uploaded Tikni BMP, one or more **reference images**, one or more **design options** (for multi-file decks — one option = one slide/colourway using the same base spec), and produces one generated PPTX + one generated PDF per generation run.
- Each **design option** has its own set of **colour slots** (ordered list of `{sequence_no, hex, area_pct, grc_ars_code, code_source: 'manual'|'auto_read'}`), extracted from that option's BMP and annotated with a GRC/ARS code — manually for now, auto-read once Section 2.5 item 5 is resolved (Section 4.2 item 2).
- Spec fields (size, shape, quality, fibre, dyeing technique, finish edge/pile height/pile type/backing/wash, width, length, PD/PID/Project#, design code, construction, notes, date) belong to the record (JLI/B2C share this shape) rather than per-option, since the meeting states the rug spec is the same across design options in one deck — only the picture and colours vary per option. **Confirm this assumption with DnD** — it's inferred from "same rug spec across slides" in the samples, not stated outright.
- **Visibility / roles (confirmed requirement):** a **creator** can only see the `cad_layout_records` they made. An **admin** can see every record from every designer, plus a usage view aggregating record counts per `employees.id` (who's using the tool, how much). Recommend modeling the admin flag the same way `team-members` already models cross-cutting access — a permission key (e.g. `cad_layout_admin`) checked via the existing `employee_has_permission()` / `department_access_grants` vocabulary (AGENTS.md / `architecture.md`'s per-module notes) rather than inventing a parallel roles table for this one module.

### 8.3 Storage plan for BMP / reference images / generated outputs
- **Recommendation, pending sign-off:** a **private** Supabase Storage bucket (e.g. `cad-layout-files`), not public like `driver-photos`/`employee-avatars` — the raw BMP must never be reachable by URL guess, so signed/expiring URLs are required, unlike the existing public-bucket precedents. This still requires the same kind of explicit AGENTS.md Section 1 override those two buckets recorded — not a silent reuse.
- **Why not self-hosted S3 (AGENTS.md's actual default):** no self-hosted S3 client, credentials, or helper exists anywhere in this repo yet (checked — nothing beyond `packages/ui-kit`'s `ImageUploadField.tsx` UI component and env-var scaffolding in apps that already overrode to Supabase Storage). Building that integration from zero, just for this one module, is a bigger decision than this PRD should make unilaterally — flagging as an explicit choice for Section 12 sign-off: either (a) stand up the org's first real self-hosted S3 integration here, or (b) request a third recorded Supabase Storage override, private-bucket variant.
- Generated PPTX/PDF outputs live in the same bucket, keyed by record/option id, retained for audit (Section 2.1's "no audit trail" gap) rather than being download-and-discard.

### 8.4 Colour ordering & extraction — findings, and what still needs confirming with DnD
The meeting states the **tool** should order colours by area covered, largest first — that's the target behaviour to build, not a description of how the existing manual decks were made. The two sample PPTX files are current *manual* output, produced before any tool existed, so they aren't expected to already follow a rule that only applies once the tool exists. What they're useful for is proving the extraction pipeline works, and surfacing a couple of details worth confirming before the ordering/mapping logic is finalized.

**Extraction is proven accurate:** every colour-slot fill in both decks that corresponds to a real palette entry matches the BMP's extracted hex value **exactly** (12/13 slots in the JLI deck, 19/25 in the Disney/B2C deck — see below for the rest). That confirms the Pillow-based palette read (colour + pixel-area per palette index) is the right technique and produces correct values; ordering is a separate, open question:

- **`TAQ-622-14-4X19...bmp` vs. the JLI template's colour slots:** the manual deck's slot order (#1=`D1CCC0` 0.67% of pixels, #4=`BDBDAE` 24.9%, …) doesn't match area rank. Since this is manual legacy output, that's expected, not a defect — but it means **the largest-area-first rule as the tool's target behaviour still needs an explicit "yes, build it that way" confirmation from DnD**, ideally checked against a layout DnD actually approves once the pilot (Section 11.1/D2) produces one.
- **`SHm-4.bmp` vs. the Disney/B2C template's colour slots:** same observation — manual slot order doesn't track area rank (e.g. the largest-area colour, `#9B3549` at 14.7%, sits in slot #8, not #1).
- **Action, not a contradiction to resolve in this PRD:** Section 2.5 item 4 stays open until DnD confirms the area-descending rule should be applied literally by the tool. This PRD does not conclude the transcript is wrong — it concludes the manual samples can't be used as a stand-in for that confirmation.

**Unmatched colour-slot fills — need a shape-mapping spike to explain, not an assumption baked in now:**
- **JLI deck:** across the 4 content slides, one colour-slot shape per slide (`#987C69`, labelled `"#10:"`) doesn't match any colour in the `TAQ-622...bmp` palette. It's the *second* shape labelled `"#10:"` on each slide — the deck already has a correctly-matched `#10` slot (`E0D4C5`) elsewhere. The likely explanation is a stale/leftover shape from copy-pasting an earlier version of the template (a spare colour box never cleaned up or relabelled), not a real 13th palette colour — but this is a hypothesis, not confirmed.
- **Disney/B2C deck:** 6 of the 25 colour-slot shapes (slots #1–#5 and #10) have fills that are close to, but don't exactly match, entries in `SHm-4.bmp`'s palette (e.g. slot #1's `#09255F` vs. the BMP's nearest `#08245C`). One plausible explanation, given the template's own printed disclaimer about consulting "accrual yarns to ensure color precision": these swatches were manually colour-corrected by the designer after initial extraction, while the rest were left as originally read. Also unconfirmed.
- **Why this matters before building:** if either explanation is right, the fill engine should leave those specific shapes alone (or treat them as designer-adjustable after auto-fill) rather than trying to force every colour-slot shape to match a BMP palette entry 1:1. The shape-mapping spike (Section 8.1) should confirm one of these theories — or surface the real one — against an actual DnD-confirmed layout before the mapping logic is written.

## Appendix B — Findings from the samples worth flagging (summary)
1. **Colour ordering needs confirming, not "fixing":** the transcript describes the area-descending rule as the *tool's* target behaviour. The two real samples are *manual, pre-tool* output, so their not following that rule isn't a contradiction — but it also means the samples can't stand in for DnD explicitly confirming the rule should be applied literally (Section 8.4). Extraction accuracy itself is proven (hex values match exactly).
2. **A handful of colour-slot fills in each sample don't match any BMP palette colour** — 1 recurring shape per slide in the JLI deck (likely a stale leftover, duplicate `#10` label), and 6 of 25 in the Disney/B2C deck (likely manual colour-precision correction after extraction, per the template's own disclaimer text). Both are hypotheses; the shape-mapping spike (Section 8.1/8.4) needs to confirm before the fill engine's mapping logic is finalized.
3. **Colour codes: target is auto-read from the Tikni file, not permanent manual entry.** The meeting's 10:30 mark states DnD's team will be told to write GRC/ARS codes into the Tikni file itself so the tool can pick them up automatically. This PRD builds manual entry as the real Phase 1 feature and treats auto-read as a follow-on once DnD shares what that legend actually looks like (Section 2.5 item 5).
4. **JLI sample is a mostly-filled template, not blank:** size/shape/quality/fibre/finish fields already have real values in all 5 slides; only `Project#:`, `Construction:`, and `Notes:` are left blank. Worth confirming with DnD whether some fields are genuinely per-slide-identical defaults vs. always-manual.
5. **Disney/B2C sample is a real filled example, not a blank template** — useful as a "target output" reference, but means it can't be used directly as the template to copy structure from without stripping its sample data first.
6. **BOM Checker (the structural reference) deviates from AGENTS.md itself** — PM2/SSH deployment instead of Vercel, and direct-RLS writes instead of Edge-Function-only writes. This PRD does not inherit those deviations silently; it follows AGENTS.md and flags where CAD Layout needs its own explicit exception request instead (Section 4.4, 5.1). Any folder-naming cleanup to match (`apps/dnd/...`) is explicitly out of scope here (Section 4.4).
7. **Self-hosted S3 (AGENTS.md's stated default) has no working precedent anywhere in the repo** — every override to date used Supabase Storage instead. This PRD surfaces that gap explicitly (Section 8.3) rather than quietly picking a side.
